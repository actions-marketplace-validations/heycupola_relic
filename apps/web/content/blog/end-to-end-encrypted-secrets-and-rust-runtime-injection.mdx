When developers look for a way to manage environment variables, they usually end up choosing between two extremes:

1. **Plaintext `.env` files on disk:** Fast and familiar, but easy to lose when switching machines, risky to send over Slack, and readable by any process, npm postinstall script, or AI assistant running on your laptop.
2. **Server-decrypted cloud secret managers:** Convenient for teams, but the vendor's servers hold the keys to decrypt your secrets, and syncing variables to deployment platforms requires giving a third-party cloud service write tokens to your production infrastructure.

We built [Relic](https://withrelic.com) to combine the speed of a local `.env` editor with strict client-side encryption and a memory-safe Rust runtime runner.

## 1. Client-Side Encryption Model

In Relic, encryption and decryption happen entirely on your machine (`packages/crypto`). Our backend only stores ciphertext.

### User Keys and Master Password

When you set up Relic, your device generates a 2048-bit RSA-OAEP key pair:

1. Your master password is run through **Argon2id** (64 MB memory, 3 iterations, 4 lanes) with a random 16-byte salt to derive a 256-bit AES key.
2. Your RSA private key is encrypted locally with **AES-256-GCM** using that derived key.
3. Only the encrypted private key, public key, and salt are uploaded to the server. Your master password never leaves your machine and is stored in your OS keychain (macOS Keychain with Touch ID, Windows Credential Manager, or Linux Secret Service).

### Project Keys and Team Sharing

Each project has its own random 256-bit AES key:

- Every secret value (and every historical version in `relic history`) is encrypted on your device with AES-256-GCM using the project key.
- The project key itself is wrapped with your RSA public key.
- When you share a project with a teammate, your device unwraps the project key and re-wraps a copy with your teammate's RSA public key.
- When you revoke a collaborator with key rotation, your device generates a fresh AES-256 project key, re-encrypts all current secrets and history entries locally, and re-wraps the new key for remaining collaborators and active service accounts.

## 2. The Rust Runner: Injecting Secrets Without Writing to Disk

When you run `relic run -e production -- npm start` or open a session with `relic shell -e development`, Relic does not write a temporary `.env` file.

Instead, the CLI decrypts the environment in memory and passes the key-value pairs over Bun FFI (`dlopen`) into a native Rust library (`packages/runner`):

- **Clean Process Environment:** The runner spawns your command with a cleared environment (`env_clear()`), passing only an explicit allowlist of essential system variables (`PATH`, `HOME`, `USER`, `SHELL`, `TERM`, locale, `TMPDIR`, `TZ`) plus your decrypted secrets. Relic credentials such as `RELIC_SERVICE_TOKEN` or `RELIC_PASSWORD` are stripped automatically.
- **Memory Zeroing:** Secret strings are held in `Zeroizing<String>` (from the `zeroize` crate) so their memory is overwritten with zeroes as soon as they are dropped. Buffer memory on the TypeScript side is also zeroed immediately after the FFI call.
- **Core Dump Prevention:** On Unix platforms, the runner sets `RLIMIT_CORE` to `0` before spawning the child process so a crash cannot dump plaintext secrets to disk.
- **Signal Forwarding:** `SIGTERM` and `SIGINT` (or console control events on Windows) are forwarded cleanly to the child process.

## 3. Direct Platform Sync (`relic push`)

Many cloud platforms (Vercel, Cloudflare Workers, GitHub Actions, Fly.io) need secrets stored in their own runtime stores.

Traditional secret managers sync to these platforms from their backend servers, which means you have to hand over a long-lived `VERCEL_TOKEN` or `CLOUDFLARE_API_TOKEN` to a third party.

With `relic push`, synchronization happens directly from your machine (or your CI runner):

```bash
relic push -e production --target vercel
relic push -e staging --target cloudflare --wrangler-env staging
relic push -e production --target github --github-env production
relic push -e production --target fly
```

Relic decrypts the environment locally, compares it against the destination platform, shows a names-only diff plan (`+` to add, `~` to update, `-` to prune, `=` unchanged), and sends the values straight to the platform's API or CLI over stdin:

```text
  Push plan -> Vercel prj_8f2a (production)

    + STRIPE_WEBHOOK_SECRET
    ~ DATABASE_URL
    = NEXT_PUBLIC_APP_URL

  1 to add, 1 to update, 1 unchanged
```

## 4. Passwordless CI/CD with Service Accounts and OIDC

For CI/CD pipelines, each service account has its own independent RSA-2048 key pair protected by HKDF-SHA256 and a high-entropy `RELIC_SERVICE_TOKEN`.

To prevent a leaked token from being used outside your pipeline, you can attach an [OIDC trust policy](https://docs.withrelic.com/guides/oidc) scoped to your repository and branch:

```bash
relic service-account create \
  --name "prod-deploy" \
  --github your-org/your-repo \
  --branch main
```

At runtime, Relic requires both the service token (to perform client-side decryption) and a valid OIDC JWT signed by GitHub Actions or GitLab CI (to verify identity). Neither credential works on its own.
